02 — What is broken

Twenty-three findings, from code and data

These come from reading the code and querying the database. They are not yet confirmed by clicking through the app — that is section 07, and it happens after you approve the permission changes, because most of these flows cannot currently be reached by the people who are supposed to run them.

Stops the flows you asked me to test

B1
Nobody can approve a stock entryBlocks

The single global approval step names the Central Stock Manager role, and that role has no members. Approval refuses unless your role is the step's role, with only stock.scope.all as an escape hatch — so today only Phani and the Admin account can approve anything. Kiruba, who you want approving stock entries, cannot.

src/lib/actions/stock.ts:532–537

B2
Approval authority is decided by role name, not by permissionModel

The same check, and the dashboard's review queue, compare the approver's role identity to the step. That is the one thing the permission model says must never happen, and it is why B1 cannot be fixed by handing anyone a key.

src/lib/actions/stock.ts:532 · src/lib/actions/dashboard.ts:157–174

B3
Any approver can approve any site's central stockScope

The "only your own department" guard is skipped when the entry has no department — and central stock never has one. There is no location guard alongside it, so an R&D manager in Bengaluru could approve goods received in Hyderabad.

src/lib/actions/stock.ts:517–524, 593–599

B4
A purchase order can be over-received through draftsBlocks

Outstanding quantity is checked when the entry is created, counting only submitted and approved entries. Two drafts can therefore each claim the full outstanding amount, and submitting re-checks nothing. Order 10, book two drafts of 10, submit both: 20 delivered against a 10-unit line.

src/lib/actions/stock.ts:247–269 vs 415–502

B5
Editing an entry never re-checks the order it is booked againstBlocks

updateStockEntry accepts purchaseOrderLineId straight from the form and validates none of it — not the product, not the quantity, not whether the order is still open. A rejected entry for 5 can be edited to 500 and resubmitted against the same line.

src/lib/actions/stock.ts:309–413

B6
An order closes on submission, then stays closed if the entry is rejectedBlocks

Delivered counts a submitted entry, so the order auto-closes the moment the operator submits. If the approver then rejects it, delivered drops back to zero but the order stays CLOSED — deliberately, since closing is meant to be a decision. Here it was never a decision, and the outstanding goods are now invisible.

src/lib/procurement-delivery.ts · src/lib/actions/procurement.ts:718–747

B7
Approving an entry does not re-sync its orderModel

syncPurchaseOrderFromEntry is called on create and submit, never on approve or reject. Combined with B6, an order's status depends on a status the entry may not keep.

src/lib/actions/stock.ts:504–578

B8
An engineer cannot see stock at another site, so cannot know to ask for itBlocks

You want an engineer to find stock across the sites' central stores and, failing that, request a dispatch from wherever it is. But the Fulfilment planner — the only cross-site view — narrows to the viewer's own site for anyone without stock.scope.all. Cross-site readiness is currently visible only to Super Admin and Admin, which makes the feature unusable for the two roles it exists for.

src/lib/actions/fulfilment.ts:126–134

B9
Dispatch operators cannot see stock at allBlocks

The role carries two scope keys but not stock.view, so the scopes grant nothing and the Stock Entries page is refused. It also carries both stock.scope.department and stock.scope.location; the wider one wins, so the first is dead weight.

B10
An engineer's role has no permissionsBlocks

Production Engineer holds nothing, so Deepa signs in to an empty dashboard. R&D Engineer holds four keys and none of them touch stock, so Raghava cannot see a product, let alone request one.

Data leaks across a boundary

B11
Site-scoped people get company-wide dashboard figuresScope

The dashboard narrows its numbers for own and department scope but passes nothing for location scope, so it falls through to the unfiltered branch. A Bengaluru operator's tiles count every entry in the company — and the value tile too, if they hold stock.value.view.

src/app/(dashboard)/dashboard/page.tsx:44–47

B12
Every dashboard action is ungatedScope

Nothing in src/lib/actions/dashboard.ts calls requirePermission. These are server actions, so any signed-in person can call them directly regardless of what their page renders. getSearchableActivity returns activity-log lines to anyone; getDashboardStats returns headcount and the last ten log entries.

B13
The recycle bin is everyone's, not your ownScope

You asked for each person to have their own bin. getRecycleBin returns everything anyone deleted, with no filter on who deleted it, and getRecycleBinCount has no permission check at all.

src/lib/actions/recycle-bin.ts:105–140

B14
A department-scoped person can pull another site's central stockScope

The transfer picker offers every entry with no department — company-wide — because it filters on department without also filtering on location. A Bengaluru engineer can request Hyderabad's central stock straight into their department, skipping dispatch entirely. The stock list gets this right; the picker does not.

src/lib/actions/requests.ts:552–566

B15
Approving a transfer ignores dispatch and build commitmentsScope

Every other surface asks availableQuantity(), which subtracts issues, pending transfers, dispatches and builds. Transfer approval subtracts issues only, so it will happily move stock already loaded onto a consignment.

src/lib/actions/requests.ts:465–471

Permission-model debt

B16

Super Admin and Admin see everything, Department Manager sees their department, everyone else sees only their own actions — decided by string comparison on the role name. An Auditor granted activity.view would see nothing but their own clicks, and no new role can ever be given department-wide activity.

src/lib/actions/activity.ts:111–135

B17
Procurement activity cannot be separated from stock activityModel

Intents and orders sit inside the "Stock in" category. Your brief gives Shravani procurement activity but not stock-entry activity, and today that combination cannot be expressed.

src/lib/activity-categories.ts:17–28

B18

Only assets.view does anything; creating an asset is gated on stock.move instead. "Manage assets" is therefore not currently a grantable capability.

B19

B20

B21

B22

04 — Model changes

Six changes to the permission model

Each of these exists because the brief asks for something the current model cannot express. They are the reason this is a plan and not a config change.

0 · A person can hold more than one role

You asked whether this is possible. It is, and it is the right answer for Uday and Kiruba — both of whom do two jobs, and both of whom I was otherwise about to paper over with a fistful of personal grants.

The shape. User.roleId stays as the primary role — it is what the badge shows, what the directory filters on, and what the hierarchy rules read. A new UserRole join table carries any additional roles. Permissions become the union of every held role plus the person's individual grants; the hierarchy level becomes the strongest (lowest) of the roles held. Nothing historic references a role, so there is no data at risk.

What it touches. unionPermissions() in src/auth.ts (two call sites), the session shape in next-auth.d.ts, an "Additional roles" card on the user profile, the directory filter matching any held role, and the role-delete guard, which must now also refuse a role held as a secondary. About a dozen files, none of them deep.

Two things it does not solve, which is why it lands before the rest.

It does not settle the scope conflict. Holding Stock Entry Operator (stock.scope.own) and Dispatch Operator (stock.scope.location) together still resolves widest-wins to the whole site — so Uday sees all of Bengaluru's stock either way. That is a judgement call about Uday, not a mechanism (question 1 in section 08).

And it makes every remaining role-name check ambiguous — "is this person a Department Manager?" has no single answer once a person holds three roles. Stock approval (B1, B2) and activity breadth (B16) must move to permissions first, or multi-role will silently break them.

1 · Stock approval becomes a permission, not a role

The approval flow keeps its steps and their order — that is a real feature — but the step's role becomes who is expected to do it, not who is allowed to. Authority moves to stock.approve, narrowed by a new location guard so an approver only ever acts on entries received at their own site. Fixes B1, B2, B3 together, and lets Kiruba approve without inventing a role for him.

2 · Activity gains a scope family

New keys activity.scope.all, activity.scope.department, activity.scope.own, resolved widest-wins exactly like stock scope, replacing the three role-name comparisons. Fixes B16 and gives you "activity log of his department" as a grant rather than a job title.

3 · The recycle bin gains a scope

recyclebin.scope.all versus own. Without the wide key you see only what you deleted — which is what makes "everyone has access to their own recycle bin" safe to grant to all nine people. Fixes B13.

4 · Procurement becomes its own activity category

Intents and orders move out of "Stock in" into a new activity.view.procurement. Fixes B17 and lets Shravani have buying history without receiving history.

5 · Assets gets real management keys, and cross-site readiness opens up

The four dead asset keys (B18) are wired to the Assets page: assets.create gates the New Asset dialog alongside stock.move, assets.edit gates correcting a holding, assets.transfer gates the transfer queue. Separately, the Fulfilment planner stops narrowing to one site: availability counts per site are shown to anyone holding fulfilment.view, while the underlying stock entries stay behind the usual scope. Seeing that Hyderabad holds nine of something is what makes asking for them possible; it does not reveal what they cost or who supplied them. Fixes B8, B9, B18.

6 · A bill of materials records the department that wrote it

You want a manager approving their own department's work, and the model could not express that because a bill of materials belongs to a product and a product belongs to nobody. So the submission carries the department, not the product: a new authorDepartmentId on BillOfMaterials, stamped from the author at submit time. bom.approve then only reaches submissions from your own department, unless you hold full scope. Raghava's work goes to Manohar, Deepa's to Kiruba, and neither can sign off the other's.

Versions written by someone with no department (an admin fixing something) carry no department and stay approvable by anyone holding the key — otherwise an admin correction could become unapprovable.

7 · You cannot answer your own request

Ashish is the only pair of hands in Hyderabad, so "accept" was going to be a handshake with himself. The rule is now explicit and applies to everyone: whoever raised something can never be the one who answers it.

  • acceptDispatch and rejectDispatch refuse when the caller created the consignment.
  • acceptSiteRequest and rejectSiteRequest refuse when the caller raised the request.

Confirming delivery is deliberately left alone — receiving goods you asked for is the normal case, not a self-approval. The same guard already exists for bills of materials; this makes it consistent across the three places it was missing.

Everything else in section 02 is a straightforward repair inside the existing model: PO integrity (B4–B7), dashboard gating and scoping (B11, B12), transfer scope and availability (B14, B15), and the four configuration corrections (B20–B23).

07 — The test run

One pass through every flow, in the order the business runs them

This is the script I would follow, signing in as each person in turn against the real database. Each step names who is acting and what should happen. A step that fails is a bug report; a step that succeeds for the wrong person is also a bug report.

Setup

  • Sign-in for all nine accounts confirmed first — an unusable account invalidates everything after it.
  • Two products used throughout: a raw material (bought in, has a vendor) and a finished product with a published bill of materials.
  • Existing data is left alone. Every record created below is prefixed so it can be identified and removed afterwards.

08 — The consolidation pass

Stripping it back to a first build

You want to read this project phase by phase, and you are reading your first Next.js and TypeScript codebase while you do it. So the goal is not "fewer lines" for its own sake — it is that every file you open should be explicable in a sentence, and nothing you read should be a thing that no longer runs. Here is exactly what I would do, measured against what is actually there.

1 · The history goes

Twenty migration folders and eighteen one-off scripts record how the project got here. That is 3,689 lines in prisma/, of which about 1,900 exist only to patch a database that has already been patched.

The one thing I will not do without you saying so. Your database has real data in it — 14 stock entries, 2 purchase orders, 4 dispatches, a build. The destructive path — reset and re-seed — gives you a spotless database and loses everything in it.

4 · The comments are rewritten to one rule

There are 1,912 comment lines in src/. The problem is not the count, it is that they are three different things wearing the same clothes: genuine explanation, an argument with a decision made two weeks ago, and narration of the line below. Reading them, you cannot tell which you are getting. Every comment gets re-judged against this:

  1. Every file opens with a short header — what it is, who calls it, and which rule it owns. Three to six lines, never more. Open any file and you know where you are.
  2. Every server action gets a one-line contract — who may call it, what it changes, what it gives back. This is the layer you will spend the most time in.
  3. Inline comments only where the code cannot speak for itself — a business rule, a guard whose absence would be a bug, a line that looks wrong and is not.
  4. Deleted on sight: narration of the next line; changelog prose ("this used to be X, which was wrong because…") — that belongs in git history, not in the file you are trying to read; and the same explanation repeated in three files, which is kept in exactly one.
  5. Added: a FLOW marker at each step of the seven main journeys, so grep "FLOW: purchase" walks you through intent → verify → order → receipt → close in reading order. This is the part aimed squarely at reading it phase by phase.

My estimate is that comment volume ends up roughly where it started — a good third deleted, a similar amount added where there is currently nothing at all. What changes is that all of it is load-bearing.
